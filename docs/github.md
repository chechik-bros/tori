# איך עובדים עם GitHub ביחד

## המושגים

תחשבו על Google Docs במצב "הצעות", רק לפרויקט שלם של קוד.

| מושג                  | מה זה בפועל                                                   |
| --------------------- | ------------------------------------------------------------- |
| **Repository**        | תיקיית הפרויקט. עותק אחד ב־GitHub, ועותק אצל כל אחד מכם במחשב |
| **main**              | הגרסה הראשית. תמיד עובדת, ועולה לאוויר אוטומטית               |
| **Branch (ענף)**      | עותק צדדי שבו עובדים על משימה אחת, בלי לגעת ב־main            |
| **Commit**            | שמירה עם הערה, כמו נקודת שמירה במשחק. נשארת אצלך במחשב        |
| **Push**              | מעלה את השמירות שלך ל־GitHub                                  |
| **Pull**              | מוריד ממנו את מה שהשני העלה                                   |
| **Pull Request (PR)** | בקשה: "תכניסו את הענף שלי ל־main". השני בודק ומאשר            |
| **Merge**             | הכנסת הענף ל־main                                             |
| **Conflict**          | שניכם שיניתם את אותה שורה, ו־Git לא יודע איזו גרסה לקחת       |

```
main        ●───────────────●───────────────●──────
             \             ↗ (B2 נכנס)      ↗ (A2 נכנס)
b/slots       ●────●─────●                /
               \                         /
a/services      ●────●────●────●────●───
```

כל אחד עובד על ענף משלו, במקביל. כשמשימה גמורה, היא נכנסת ל־main, והשני מושך אותה אליו.

## פעם אחת: הכנה

```bash
git config --global user.name "השם שלך"
git config --global user.email "המייל של GitHub"
```

מי שלא יצר את הפרויקט מוריד אותו:

```bash
git clone https://github.com/YOUR_ORG/tori.git
cd tori
npm install
```

ומעתיק את `.env.local` שקיבל מהשני.

## כל משימה, אותם צעדים

**1. מתחילים מ־main עדכני.** זה הצעד הכי חשוב. רוב הבעיות מגיעות משכחה שלו.

```bash
git checkout main
git pull
```

**2. פותחים ענף למשימה.** האות שלך, ואז שם קצר באנגלית:

```bash
git checkout -b a/services-page
```

**3. עובדים.** כותבים קוד, בעצמך או עם Claude/Cursor. בכל שלב אפשר לראות מה השתנה:

```bash
git status
```

**4. שומרים שלב (commit).** כל פעם שחלק קטן עובד:

```bash
git add -A
git commit -m "Add services list"
```

**5. מעלים ל־GitHub.** לפחות בסוף כל ערב עבודה, גם אם המשימה לא גמורה. זה גם גיבוי.

```bash
git push -u origin a/services-page
```

בפעמים הבאות באותו ענף מספיק `git push`.

**6. לפני שמבקשים בדיקה, מושכים את מה שהשני הכניס בינתיים:**

```bash
git pull origin main
```

אם הכל עבר בלי הודעת שגיאה, מריצים את האתר ובודקים שעדיין עובד, ועושים `git push`.

**7. פותחים Pull Request.** ב־GitHub, בדף הפרויקט, מופיע כפתור צהוב **Compare & pull request**.

- כותרת: `A2 עמוד שירותים`
- בתיאור: `Closes #7` (המספר של המשימה), כדי שהמשימה תיסגר לבד במיזוג
- ממלאים את התבנית ולוחצים **Create pull request**
- כותבים בקבוצה: "A2 מוכן לבדיקה"

**8. השני בודק.**

- נכנס ל־PR. בתגובות יש קישור תצוגה מ־Vercel: פותח אותו ובודק שזה עובד, גם בטלפון.
- בלשונית **Files changed** רואה מה השתנה.
- **Review changes → Approve**. או **Request changes** עם הסבר מה לתקן.

**9. ממזגים.** מי שפתח את ה־PR לוחץ **Squash and merge**, ואחר כך **Delete branch**. תוך דקה האתר באוויר מתעדכן.

**10. חוזרים לצעד 1** עם המשימה הבאה.

## ככה זה נראה במקביל

| יום      | אתה (A)                                                     | אח שלך (B)                           |
| -------- | ----------------------------------------------------------- | ------------------------------------ |
| ראשון    | צעדים 1–2: ענף `a/services-page`. עובד ושומר                | צעדים 1–2: ענף `b/slots`. עובד ושומר |
| שני      | ממשיך לעבוד. `git push` בסוף הערב                           | מסיים, פותח PR, כותב בקבוצה          |

| שלישי    | מסיים. `git pull origin main` מכניס לענף שלך את B2. פותח PR | בודק את שלך ומאשר                    |

אף אחד לא חיכה לשני, ואף אחד לא נגע בקבצים של השני.

## קונפליקט: מה עושים

זה קורה רק כששניכם שיניתם את אותן שורות. אם כל אחד נשאר בתיקיות שלו, זה יהיה נדיר.

`git pull origin main` יכתוב `CONFLICT` ושם של קובץ. בתוך הקובץ יופיע:

```
<<<<<<< HEAD
השורה שלך
=======
השורה שלו
>>>>>>> main
```

1. ב־VS Code או ב־Cursor מופיעים מעל הקטע כפתורים: **Accept Current** (שלך), **Accept Incoming** (שלו), **Accept Both** (שניהם).
2. בוחרים, ומוודאים שלא נשארו סימני `<<<<<<<` בקובץ.
3. שומרים את הקובץ ומסיימים:

```bash
git add -A
git commit -m "Resolve merge conflict"
```

לא בטוח מה לבחור? מתקשרים לשני. או מבקשים מ־Claude: "יש קונפליקט, תפתור אותו ותסביר לי מה בחרת ולמה".

## לא חייבים להקליד פקודות

- **Claude Code:** אפשר לבקש במילים: "תפתח ענף למשימה A2", "תעשה commit ו־push ותפתח PR". Claude מריץ את הפקודות בשבילך. כדאי עדיין להבין מה קורה, ולכן המדריך הזה.
- **Cursor ו־VS Code:** בסרגל הצד יש אייקון Source Control. משם עושים commit, push ו־pull בלחיצות.
- **GitHub Desktop:** אפליקציה חינמית שמראה הכל בצורה ויזואלית, למי שמעדיף.

## טעויות נפוצות

| מה קרה                                     | מה עושים                                                                      |
| ------------------------------------------ | ----------------------------------------------------------------------------- |
| התחלתי לעבוד ושכחתי לפתוח ענף, אני על main | עוד לא עשית commit? `git checkout -b a/my-task` מעביר את כל השינויים לענף חדש |
| `Your branch is behind`                    | `git pull`                                                                    |
| `rejected` ב־push                          | מישהו העלה לפניך לאותו ענף: `git pull` ואז שוב `git push`                     |
| לא מבין איפה אני                           | `git status` אומר באיזה ענף אתה ומה השתנה                                     |
| ה־PR ענק ואף אחד לא רוצה לבדוק             | משימה אחת לכל PR, יום עד שלושה ימי עבודה                                      |

## הכללים שלנו

1. לא עובדים ישירות על main.
2. כל משימה בענף משלה, עם PR.
3. בודקים PR של השני תוך 24 שעות.
4. `git push` בסוף כל ערב עבודה.
5. `.env.local` לא נכנס לגיט אף פעם (`.gitignore` מטפל בזה).
6. שינוי במסד: הודעה בקבוצה לפני שמתחילים.
